Extracting PQXDH to Lean — workarounds and bisections

A field report on extending the Aeneas/Charon Rust→Lean pipeline to cover libsignal-protocol's PQXDH (Post-Quantum X-DH) key agreement. Two atomic commits land both pqxdh_initiate and pqxdh_accept as transparent Lean defs, with libcrux ML-KEM-1024 as the axiomatic FIPS-203 leaf.

3. Why two phases

After Phase A, pqxdh_initiate was extracting cleanly but pqxdh_accept hit a “There should be no bottoms in the value” symbolic-interpreter crash inside Aeneas (interp/Interp.ml:550) — the AENEAS-010 signature.

This is a hard crash, not a translation gap. Two routes were viable:

  • (a) Leave pqxdh_accept axiomatic and document the gap.
  • (b) Bisect Aeneas's failure on the real body, find the minimal trigger, and apply a source rewrite in pqxdh.rs that preserves semantics but routes around it.

We picked (b) because the function is the centerpiece of the recipient side of the protocol — making it axiomatic would defeat the point of extraction. The cost was one bisection session and one Rust source change.

5. AENEAS-012 codegen mismatch

A new shortcoming surfaced during Phase A and is worth calling out because the workaround pattern is reusable.

The symptom: kem.KeyPublic.encapsulate(...) is defined in generated Funs.lean with a 2-tuple return shape (Result × R), but at the call site inside pqxdh_initiate, Aeneas emits a 3-tuple destructure:

let (r3, csprng1, encapsulate_back) ← ...   -- 3-tuple at call site

The third element — a phantom “backward continuation” — was never produced by the definition. Lean rejects with expected a product type, got R.

The root cause is a context-sensitive emitter pass: when the &mut R argument is reached through the blanket impl CryptoRng::Blanket (DerefMut R), Aeneas's emitter assumes a backward continuation will be produced (the lens-style propagation typical of &mut through DerefMut). But the definition of encapsulate does not actually produce one — the trait dispatch resolves to a concrete implementation that never threads a phantom back through. The result is an arity mismatch between definition site and call site for the same function.

The workaround is purely textual: three tweaks.substitutions in aeneas-config.yml that rewrite the call site to drop the third element of the destructure and replace the back-continuation application with identity:

- find: "let (r3, csprng1, encapsulate_back) ←"
  replace: "let (r3, csprng1) ←"
- find: "let (r4, csprng1, encapsulate_back) ←"
  replace: "let (r4, csprng1) ←"
- find: "let csprng2 := encapsulate_back csprng1"
  replace: "let csprng2 := csprng1"

These run after npm run aeneas-extract writes the file, before lake build reads it. The find-strings are tied to the specific variable names Aeneas emits for pqxdh_initiate — a future Aeneas release that renames intermediates would break the substitution, but that's a known fragility of the tweaks mechanism and is the right tradeoff while the upstream fix is open.

Full reproduction + suggested upstream fix in the catalog under AENEAS-012.

6. The AENEAS-010 bisection

The Phase B blocker was an Aeneas symbolic-interpreter crash:

[Error] [Internal] There should be no bottoms in the value (1)
  raised at interp/Interp.ml line 550

Catalogued as AENEAS-010. Diagnosing it required progressive simplification of pqxdh_accept until the failure went away, then adding things back one at a time to isolate the trigger.

Bisection table:

VariantResult
Remove the canonical-check if block entirelyextracts
Keep is_canonical() call, drop the early-returnextracts
Replace early-return with unit variant Err(InvalidKeyAgreement)extracts
Replace with 2-arg variant without &'static str (BadKeyLength(KeyType, usize))extracts
Replace with 1-arg variant with &'static str (InvalidSessionStructure("..."))crashes
Original 2-arg variant with &'static str (InvalidMessage(..., "..."))crashes
The trigger is specifically the &'static str payload in an early-return Err variant. Everything else that looked suspicious — the ?-propagation, the decapsulation chain, the optional if let Some(...) path, the Vec::with_capacity + extend_from_slice builder — extracted cleanly in isolation. Only the &'static str in the Err position reproduced the bottom.

Why this seems to happen (informed guess, not catalogued as authoritative): Aeneas's symbolic interpreter tracks borrows of heap-shaped values. A &'static str payload reaches the symbolic state through the early-return without ever being elaborated by a constructor that the interpreter recognizes — so when control reaches the propagation site, the value's projections evaluate to ⊥ (bottom). This is a defect in the interpreter, not in the source.

The fix in M10 is one statement:

// before
return Err(SignalProtocolError::InvalidMessage(
    CiphertextMessageType::PreKey,
    "incoming base key is invalid",
));

// after
return Err(SignalProtocolError::InvalidKeyAgreement);
The unit variant is semantically near-equivalent: a non-canonical their_ephemeral_key would have failed inside calculate_agreement one statement later anyway, surfacing the same InvalidKeyAgreement error. The change is observable only in the error-variant identity for that one input class, and the fail-fast property is preserved.

Logged in src-modifications.md as M10 with the bisection table and the upstream-issue-grade minimum failing example.

7. Namespace cascade

When the M5 extraction surface widened to include all of libsignal-protocol (vs the M4 baseline of just signal-crypto + libsignal-core), Aeneas's outer-wrap namespace changed from signal_crypto to libsignal_protocol. The change is derived from aeneas-config.yml: crate.name.

The cascade affected three layers:

  • Generated files (Types.lean, TypesPreBase.lean, etc.) — now wrapped in namespace libsignal_protocol. These auto-regenerate, so no manual work, but…
  • Hand-authored externals (TypesExternal.lean, TypesExternalPre.lean, FunsExternal.lean) — these open whatever namespace the generated files wrap in, so a one-line edit was needed in each.
  • Hand-authored specs (Libsignal/Specs/Core/Address/*.lean) — five files using namespace signal_crypto.libsignal_core.address.ServiceId — needed renaming.

A sed -i '' 's/signal_crypto\./libsignal_protocol./g' <files> batched the spec fixes; the externals were single-line edits each. If the crate name ever changes again, the cascade fires again, so this is one of those “easy to do, easy to forget” landmines.

8. What's transparent, what's axiomatic

After both phases, the trust boundary looks like this:

Transparent (real Lean defs, body reasoning available)

  • pqxdh.pqxdh_initiate — the initiator side, full body
  • pqxdh.pqxdh_accept — the recipient side, full body
  • kem.KeyPublic.encapsulate / kem.KeySecret.decapsulate — dispatch on KeyType and call the kyber1024 leaf
  • kem.Ciphertext.{serialize, deserialize} — wire format
  • All algebraic helpers (HandshakeKeys constructors, vec-byte chain, HKDF-input layout, etc.)

Axiomatic (defines the trust boundary)

  • kem.kyber1024.Parameters.Insts.*.{encapsulate, decapsulate} — the FIPS-203 ML-KEM-1024 oracle. This is the cryptographic primitive we're trusting; we are not trying to re-verify libcrux. Documented in src-assumptions.md as A03.
  • libsignal_core.curve.PrivateKey.calculate_agreement — X25519 DH. Documented as A04.
  • HKDF-SHA256 closure body — axiomatic in the closure layer.
The trust boundary is now correctly placed at cryptographic primitives rather than at protocol composition. The composition logic (the four DH operations + one Kyber encap/decap, the HKDF derivation, the byte-layout of the secrets vector) is all real Lean that a prover can step through.

9. Where to go from here

With both PQXDH entry points as transparent defs, the natural next phase is correctness proofs — symbolic execution of both bodies side-by-side under matched-key inputs, equality of the four DH operations (X25519 algebraic property A04), equality of the Kyber encap/decap shared secrets (A03), and equality of HKDF outputs (the KDF closure axiom).

A plausible ramp from smallest to largest:

  1. Byte-layout invariant for the secrets vector in pqxdh_initiate (Funs.lean lines around the Vec::with_capacity + extend_from_slice chain) — the equality of byte layouts on initiator vs recipient side. Pure data-shape reasoning, no crypto axioms used.
  2. HandshakeKeys.derive invariant — given matching secrets, the derived keys are equal. Uses the HKDF closure axiom.
  3. Full correctness theorem — initiator and recipient compute the same HandshakeKeys from matched bundles. The standard Bhargavan-paper formalization theorem.

The BAIF_GH/PQXDH/ repo has the symbolic-model formalization to bridge to once the extracted-side proofs are in place.
