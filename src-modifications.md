# Source modifications

This file precisely catalogs every modification this project has applied to
upstream Rust files in `rust/`. The verification claims of this project are
bounded by these modifications: any theorem about an affected function is only
meaningful if the corresponding assumption (`src-assumptions.md`, `A-entry`)
holds.

## Provenance

- **Upstream pinned:** libsignal commit
  `6e5a0466b35e23925ad4b3a31a8c6572471c33d9`
  (also recorded in `aeneas-config.yml: upstream.commit`).
- **Fork base:** `Beneficial-AI-Foundation/libsignal-verify` rebased onto
  upstream `6e5a0466`. The rebase carries the BAIF-inherited modifications
  catalogued in Section 1 below.
- **Machine diff:** `src-modifications.diff` — regenerated by
  `npm run src-diff`. It captures **every** divergence from upstream
  `6e5a0466` (both BAIF-inherited and this-branch-introduced). When this
  file mentions specific lines, refer to the `.diff` for the exact
  byte-level change.
- **Cross-references:** each entry links to its `charon-aeneas-shortcomings`
  AENEAS-xxx / CHARON-xxx issue ID at
  `docs/charon-aeneas-shortcomings.md`. When an upstream fix
  lands, grep this file for the ID to find all reverts needed.

## Principles

1. **Edit upstream source only as a last resort.** Prefer
   `aeneas-config.yml: opaque` / `exclude` config-level workarounds.
2. **Every modification is catalogued here precisely.** No edit to a Rust
   file under `rust/` is committed without a corresponding M-entry.
3. **Each modification whose behavior changes gets a corresponding A-entry
   in `src-assumptions.md`.** Verification claims about modified code are
   bounded by those assumptions.
4. **Modifications are reversible.** When the upstream Aeneas / Charon
   issue that motivated a modification is fixed, the modification should
   be reverted and the diff re-narrowed.

## Modification taxonomy

| Type | Meaning |
|---|---|
| `cfg-prelude-add`   | Added a top-of-crate `#![cfg_attr(...)]` enabling a Charon attribute namespace |
| `attr-cfg-add`      | Added a `#[cfg_attr(feature = "extraction", charon::...)]` annotation on an item; no behavioral change under any cfg |
| `rewrite-equivalent`| Replaced source with a semantically-equivalent form (e.g., owned field instead of borrowed) |
| `monomorphise`      | Narrowed type / feature variants (semantic narrowing; behavior preserved for the retained variant) |
| `drop-unused`       | Removed code that no extraction-target function calls |
| `drop-incompatible` | Removed code Aeneas / Charon cannot translate, with no alternative |

### M01 — `rust/protocol/src/lib.rs`: enable `charon` attribute namespace under `extraction`

- **File:** `rust/protocol/src/lib.rs` (lines 18-20 of current file)
- **Commit:** `64ed4cfa8` ("feat: enable charon attribute namespace in libsignal-protocol")
- **Type:** `cfg-prelude-add`
- **Upstream issue:** none directly — this is a *prerequisite* for being able
  to write `#[cfg_attr(feature = "extraction", charon::...)]` annotations
  in the rest of this crate. The pattern mirrors the existing preludes in
  `rust/core/src/lib.rs` and `rust/crypto/src/lib.rs` (both BAIF-inherited).

**Diff:**
```rust
+#![cfg_attr(feature = "extraction", feature(register_tool))]
+#![cfg_attr(feature = "extraction", register_tool(charon))]
```

**Justification:** Without `register_tool(charon)`, the Rust compiler
rejects `#[charon::opaque]` and `#[charon::exclude]` annotations as unknown
attributes. The cfg-gating ensures the unstable feature is only requested
when building under `--features extraction`; standard builds (the libsignal
production path) are unaffected.

**Last-resort check:** Yes. There is no alternative — the Charon attribute
namespace must be registered for downstream annotations (M02, M03) to
compile.

**Semantic claim:** None — the prelude has zero observable effect on any
code path under any cfg. The `#![feature(register_tool)]` opens a
namespace; it does not register any concrete attribute behavior. No A-entry
needed.

### M02 — `rust/protocol/src/handshake.rs`: exclude `trait Handshake` from extraction

- **File:** `rust/protocol/src/handshake.rs` (lines 26-32 of current file)
- **Commit:** `3bc37999` ("feat: workarounds for Aeneas GAT and trait-impl pre-pass issues")
- **Type:** `attr-cfg-add` + scope-limit-via-exclusion
- **Upstream issue:** AENEAS-001 (GAT in trait associated type) — see
  `docs/charon-aeneas-shortcomings.md`.

**Diff (excerpt):**
```rust
+// Excluded under the `extraction` feature: Aeneas cannot translate trait
+// associated types with parameters (`type RecipientParams<'a>`). The
+// free functions `pqxdh_initiate` / `pqxdh_accept` in `pqxdh.rs` are the
+// real extraction targets; the trait + impl below are thin glue and are
+// dropped from the LLBC.
+#[cfg_attr(feature = "extraction", charon::exclude)]
 pub(crate) trait Handshake {
     type InitiatorParams;
     type RecipientParams<'a>;
     ...
 }
```

**Justification:** The `Handshake` trait declares a GAT
(`type RecipientParams<'a>`). Aeneas's MIR analysis cannot model GATs
(they require lifetime-quantified type-family translation that the Aeneas
core does not support — see AENEAS-001). The trait is excluded entirely
from extraction. The free functions it generalises over (`pqxdh_initiate`,
`pqxdh_accept`) are the real verification targets; the trait is thin glue.

**Last-resort check:** Yes. No config-level workaround exists for GAT
handling — the GAT must be removed from Aeneas's view. The trait is
excluded rather than rewritten because the free functions it glue-wraps
are the canonical verification target.

**Semantic claim:** Behavioral equivalence depends on **A01**: the
`Handshake::accept` method (and parallel `Handshake::initiate`) on `Pqxdh`
delegates to `pqxdh_accept` / `pqxdh_initiate` and contains no other
behavior beyond return-value re-packaging. See `src-assumptions.md` A01.

### M05 — `rust/protocol/src/kem.rs`: exclude `DynParameters` trait + its blanket impl

- **File:** `rust/protocol/src/kem.rs` (lines 108-126 trait declaration, 128-173 blanket impl)
- **Commit:** *(uncommitted at time of writing — bundled with M06+M07 into one atomic "Plan A: extract encaps/decaps wrappers" commit)*

- **Upstream issue:** AENEAS-009 (Dynamic trait types not supported).

**Justification:** `DynParameters` exists solely to make `KeyType::parameters() -> &'static dyn DynParameters` work as a runtime tag-dispatch from the `KeyType` enum to the appropriate ML-KEM impl. 2. Adopt dictionary-passing translation in Aeneas (substantial upstream engineering).

**Semantic claim:** None for this entry alone — the trait + impl are *abstractions over* the concrete `kyber1024::Parameters` impl. The behavioral claim is in M07's A04 (the direct-dispatch rewrite preserves observable behavior).

### M08 — `rust/protocol/src/error.rs`: cfg-gate out `ApplicationCallbackError` variant + factory under `extraction`

- **File:** `rust/protocol/src/error.rs` (lines 83-87 variant; lines 108-116 factory function)
- **Commit:** *(uncommitted; bundled with M05+M06+M07 into Plan A commit)*
- **Type:** `drop-incompatible` (under `extraction` cfg only)
- **Upstream issue:** AENEAS-009 (the variant holds `Box<dyn std::error::Error + ...>` which Aeneas's symbolic interpreter cannot translate).

**Diff:**
```rust
     /// error in method call '{0}': {1}
+    #[cfg(not(feature = "extraction"))]
     ApplicationCallbackError(
         &'static str,
         #[source] Box<dyn std::error::Error + Send + Sync + UnwindSafe + 'static>,
     ),

+#[cfg(not(feature = "extraction"))]
 impl SignalProtocolError {
     pub fn for_application_callback<E: ...>(...) -> impl FnOnce(E) -> Self {
         move |error| Self::ApplicationCallbackError(method, Box::new(error))
     }
 }
```

**Justification:** `ApplicationCallbackError` holds a `Box<dyn std::error::Error + Send + Sync + UnwindSafe + 'static>` payload (trait-object error type for FFI callback errors). Aeneas's translation of the entire `SignalProtocolError` enum fails on this `dyn Error` field (same AENEAS-009 root cause as `kem::DynParameters`). Pattern-matching and construction sites for this variant are **exclusively** in the FFI bridge crates (`rust/bridge/shared/types/src/{ffi,jni,node}/error.rs`), which are separate workspace crates that do not depend on extraction and are not part of the verification target. Within `libsignal-protocol` itself, the variant is only declared and never used — and PQXDH never references it.

Cfg-gating the variant + its factory function out under `feature = "extraction"` removes the `dyn Error` field from Aeneas's view while preserving the production code path (`cargo check -p libsignal-protocol` without extraction still compiles unchanged; the bridge crates continue to construct and pattern-match on the variant normally).

**Last-resort check:** Three less-invasive alternatives considered and rejected:

1. *Mark the whole enum `#[charon::opaque]`.* Loses ALL variant-level reasoning in extracted Lean; PQXDH's error returns become axiomatic black boxes. Sacrifices the verification surface unnecessarily.
2. *Mark just the variant `#[charon::opaque]`.* `charon::opaque` is documented at the type / impl-block level; per-variant opacity is not in the surface API.
3. *Replace the `dyn Error` field with `String` under extraction.* Doable but requires also rewriting every construction and pattern-match site that uses the field — and those sites span four FFI bridge crates. Disproportionate blast radius for a variant PQXDH does not use.

The cfg-gate is the smallest possible change with no impact on production code.

**Semantic claim:** None for PQXDH verification. The cfg-gate-out is verification-neutral within the M5 scope.

### M10 — `rust/protocol/src/pqxdh.rs:331-338`: replace `InvalidMessage` early-return with unit-variant `InvalidKeyAgreement`

- **File:** `rust/protocol/src/pqxdh.rs` (the `is_canonical()` early-return at the top of `pqxdh_accept`)
- **Commit:** *(uncommitted; bundled with Phase B commit)*
- **Type:** `rewrite-equivalent` (semantics-preserving up to error-variant identity / logging string)
- **Upstream issue:** AENEAS-010.

**Change:**
```rust
// Before
if !parameters.their_ephemeral_key.is_canonical() {
    return Err(SignalProtocolError::InvalidMessage(
        CiphertextMessageType::PreKey,
        "incoming base key is invalid",
    ));
}

// After (M10)
if !parameters.their_ephemeral_key.is_canonical() {
    return Err(SignalProtocolError::InvalidKeyAgreement);
}
```

**Justification:** Bisection of the AENEAS-010 "no bottoms" symbolic-interpreter trigger isolated it to **early-return-with-Err where the Err variant carries a `&'static str` literal payload**. Variants confirmed:

| Variant | Result |
|---|---|
| Remove the entire `if` block | ✓ extracts |
| Keep `is_canonical()` call, drop early-return | ✓ extracts |
| Unit variant `Err(InvalidKeyAgreement)` | ✓ extracts |
| 2-arg variant without `&'static str` `Err(BadKeyLength(KeyType, usize))` | ✓ extracts |
| 1-arg variant *with* `&'static str` `Err(InvalidSessionStructure("..."))` | ✗ "no bottoms" |
| 2-arg variant *with* `&'static str` (original) | ✗ "no bottoms" |

So the trigger is specifically the `&'static str` payload — any Err variant carrying one fails. The fix substitutes a unit variant. See AENEAS-010 in `docs/charon-aeneas-shortcomings.md` for the full bisection record + upstream-bug framing.

**Last-resort check:** The early-return is itself a fail-fast optimization: if `their_ephemeral_key` is non-canonical, the immediately-following `calculate_agreement(...)?` would also fail (with `InvalidKeyAgreement`). So removing the early-return entirely would still preserve safety. The chosen rewrite keeps the early-return for performance/clarity but swaps the error-variant to one that does not carry a `&'static str` payload — a strictly less invasive change than removing the check.

**Semantic claim:** Up to error-variant identity, the original and rewritten code are equivalent on all inputs. The Rust caller chain treats both `InvalidMessage(PreKey, ...)` and `InvalidKeyAgreement` as "key agreement failed" errors. The string "incoming base key is invalid" was for human consumption (log message) only — its loss is observable only to operators reading logs, not to programmatic callers. The lower-level `calculate_agreement` ALSO returns `InvalidKeyAgreement` on a non-canonical key, so the rewritten function's error-variant on bad input is exactly what the original would have produced one statement later anyway.

**Revertibility:** When AENEAS-010 is fixed upstream (see suggested fix in `docs/charon-aeneas-shortcomings.md`), restore the original `InvalidMessage(CiphertextMessageType::PreKey, "incoming base key is invalid")` and remove the M10 comment block.
